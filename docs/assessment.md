# VoxBuild: customer brief and submission evidence

## Proposal

A fictional long-term rental marketplace, like Apartments.com or StreetEasy, wants prospective tenants to explore a room before requesting a tour. Photos and static plans leave tenants to imagine furniture layouts and home-office space. The business impact is a hypothesis to test: uncertainty may reduce qualified tour requests and create repetitive suitability questions for leasing teams. These reference brands illustrate the customer category; no claim is made about their actual systems.

Assume a self-hosted Next.js listing application, an existing AI feature using the OpenAI SDK, AWS listing/catalog/photo services, MongoDB Atlas, customer identity, and a custom web release pipeline. Review-environment queues, release handoffs, and infrastructure upkeep compete with renter features for senior engineering time. These are discovery assumptions to validate with the customer.

**Recommend a scoped planner pilot on Vercel:** Next.js/Functions provide managed delivery and request handling; Preview Deployments support review; AI SDK supplies a shared AI integration; AI Gateway supplies managed model access and routing. The existing listing application, its OpenAI SDK feature, AWS services, Atlas, and identity stay in place. Vercel augments the renter experience and takes on delivery for this new slice; it does not require a wholesale application or SDK migration.

The proposed customer journey is **existing listing → approved room/catalog context → planner → saved design → existing tour inquiry**. Listing integration, customer authorization, and tour attribution are pilot work. The actual demo uses six authored room presets, a 14-SKU furniture fixture, and a newly provisioned external Atlas cluster representing the retained customer database. Real owner-scoped saves and rereads cross that boundary; the demo does not load real listings or certify that a renter's own furniture will fit.

The central contract is simple: **the model proposes operations; the server validates and saves; the browser renders the acknowledged result.**

The bounded proof includes text and voice edits, six environment styles, and five painting designs. Use one room edit, a Gateway routing inspection, and a saved-scene reload to demonstrate the architectural contract. The earlier catalog expansion at `d5951a9` and subsequent refinements retain their dated evidence below.

| Customer friction | Recommended choice | Actual demo evidence | Pilot measure |
| --- | --- | --- | --- |
| Review queues and release handoffs delay renter experiments | Next.js/Functions + Preview Deployments for the planner | Git deployments, a working Preview, and co-deployed UI/APIs; gated promotion and rollback are unexercised | Review wait, approved change to validated release, release effort, and maintenance hours against the existing workflow |
| Provider integration and routing add upkeep | AI SDK + AI Gateway | Shared validated text path; recorded primary and policy-selected fallback saves with returned usage/cost | Effort to qualify a model, semantic success by route, cost coverage, and all-in cost per accepted interaction |
| A useful AI edit must preserve customer-owned state | Functions connect to retained Atlas through the shared executor | Real external Atlas writes/rereads, ownership checks, revision conflicts, and atomic rejection | Accepted-edit save/reload success and recovery behavior; customer identity/network integration before launch |
| Tenants struggle to picture a room before touring | A planner alongside existing listings | Authored-room interactions prove the experience; listing-to-tour integration and conversion uplift are unproven | Qualified tour inquiries per eligible visitor, suitability-support contacts, abandonment, and accessibility feedback |

## Developer experience and ROI

The engineering hypothesis is that self-service previews and a shared release workflow shorten review queues, while managed Functions, delivery, and Gateway reduce infrastructure upkeep and provider plumbing. Developers can put recovered capacity into renter features, potentially avoiding future dedicated DevOps hires around the planner. This does not eliminate operations: the customer still owns IAM/security, SSO, data governance, incident response, model evaluations, and application maintenance.

Senior engineering time belongs in the total-cost comparison. Time spent building preview environments, coordinating caches, and maintaining rollout tooling is unavailable for renter features and customer experiments. Managed delivery can shorten the path to feedback and reduce ongoing upkeep; establish the customer’s actual effort and loaded labor cost before forecasting savings. Delayed learning is an opportunity cost, not automatically lost revenue. VoxBuild uses Git deployments, previews, and Functions; canary rollout and rollback drills remain proposed, and custom cache coordination is a customer discovery topic.

[Vercel’s Next.js integration](https://vercel.com/docs/frameworks/full-stack/nextjs) combines framework support with managed deployment, rendering, and caching capabilities. This alignment can reduce setup work for an existing Next.js team, subject to compatibility checks. With [Fluid Compute’s Active CPU pricing](https://vercel.com/docs/functions/usage-and-pricing), CPU billing pauses during I/O waits; provisioned memory remains billable while requests are in flight, and invocation and model charges still apply. This is relevant to Function-based text requests and database operations. VoxBuild’s continuous voice connection uses Gateway’s relay rather than a long-running application Function. No comparative Fluid savings are measured.

[Vercel’s Factory customer story](https://vercel.com/customers/how-factory-scaled-its-cloud-backend-to-one-billion-monthly-requests-on-vercel) describes scaling its Next.js backend, internal tooling, and security without a dedicated infrastructure team. It supports the operating-model argument, not a staffing or capacity guarantee for this customer. The article’s billion-request period is inconsistent between its title and body, so this brief does not use that figure.

[Vercel’s justInCase Technologies customer story](https://vercel.com/customers/how-vercel-helped-justincase-technologies-cut-their-build-time-in-half) reports **72 hours of developer time saved per month across its team**. This published customer result supports the opportunity; it is neither a VoxBuild measurement nor a forecast for the rental marketplace.

Baseline the customer’s review wait, approved change to validated preview/production, release and rollback effort, maintenance hours, and on-call load. **Annual capacity value = recovered engineering hours/month × loaded hourly cost × 12.** Deduct incremental platform/model-usage costs, migration effort, and remaining operations costs not already reflected in recovered hours. Time redirected to product work is capacity; only an actual spending reduction or documented avoided planned hire is cash savings. Do not double-count the same hours as capacity and staffing savings, or deduct remaining operations twice. VoxBuild has no measured customer dollar savings.

The four-choice planner pilot addresses the assumed delivery and AI friction together. **If discovery does not confirm a release bottleneck**, a smaller alternative is Gateway on the existing host with the existing OpenAI SDK, after compatibility checks. AI SDK adoption remains a separate, feature-by-feature decision. Compare either option with the same customer baseline before expanding.

Expand the planner only when measured review/release effort improves by the agreed amount, all-in cost per accepted interaction stays within an agreed budget, and tour/support guardrails hold alongside technical checks. Include runtime, model/Gateway, database, network, failed/retried work, and allocated operating costs in that interaction measure; the returned text-model price alone is incomplete. Agree thresholds, sample size, and ownership before the pilot. These are proposed gates, not achieved outcomes.

## Decisions to defend

- **Keep Atlas:** it is the customer boundary and durable state owner. One-document atomic updates are sufficient for this scene model; optimistic concurrency avoids silent overwrites. Exact manual/voice command retries use retained receipts. A lost text response is recovered by reloading: `/api/scene-agent` checks revision before receipt lookup and returns `409 REVISION_CONFLICT` when the original edit already committed.
- **Constrain the model:** a fixed operation vocabulary and renderer catalog prevent executable output, arbitrary assets, and invented furniture dimensions from becoming accepted state. Provider-compatible `anyOf`/plain-field schemas are followed by strict domain validation before commit; schema portability must not weaken the authoritative checks.
- **Put voice through Gateway:** the AI SDK's normalized Realtime WebSocket flow and Gateway access/accounting surface reduce bespoke provider plumbing and consolidate text/voice usage oversight. Functions mint a 60-second single-use token with a server-only Gateway API key, then leave the media connection to browser ↔ Gateway ↔ OpenAI Realtime 2.1. Ordinary text OIDC authentication is insufficient for token minting. The trade-offs are a media relay, provider-specific capability constraints, and no implemented active-session voice failover. The application still owns permission handling, interruption, strict validation, and post-commit speech coordination. Captions use English `gpt-4o-mini-transcribe`; the Realtime model interprets audio. Gateway voice event dollar cost and serving-provider identity are unknown unless returned metadata supplies them.
- **Be honest about evidence:** the catalog is a fixture; local sample mode is not AI or cloud persistence; the verified fallback is a policy-routing test, not an outage test; photo reconstruction is deferred.
- **Ship a narrow proof:** one polished experience and a clear save/reload contract provide a stronger discovery artifact than multiple partially functioning integrations.
