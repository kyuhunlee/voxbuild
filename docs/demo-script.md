# Customer demo script

Tell one story: help renters decide whether to tour, add a bounded planner to the existing marketplace, and measure whether it earns its engineering and operating cost. Use **Case study** in its displayed order, with a five-minute live demo inside the 10–15 minute presentation. The schedule below targets 12½ minutes; it is a runbook, not a claim that the timed presentation has been rehearsed.

Use a verified public Vercel deployment in a browser that supports WebGL. Start with a fresh visitor session for a reproducible room. The current experience has **14 furniture SKUs, six room presets, and six room styles**. Keep the [assessment and dated evidence ledger](assessment.md) available for questions rather than opening with test history.

## Before presenting

Confirm the deployment reports live storage and Gateway capabilities. Rehearse the text sequence below and its saved-room reload. Prepare an accessible **branch Preview URL** in a second tab and verify that the reviewer can open it before presenting; automatic previews do not establish gated promotion. For the optional voice walkthrough, confirm the server-only `AI_GATEWAY_API_KEY`, then test microphone connection, spoken edit, interruption, and Stop. Refresh and restart voice after a deployment change. Open **Case study** for the narrative and optional full-screen view; use **Architecture → System map** for the technical flow. Opening the guide stops voice, so close it before connecting the microphone. Check the Gateway budget and keep the [latest recorded production text report](evidence/semantic-refinement-production.json) and [local Gateway voice report](evidence/gateway-voice-local.json) ready. A catalog fixture is not an AWS integration, and sample mode does not prove cloud persistence.

On November 12, voice admission is temporarily 100 starts/hour per visitor and 500/day globally; text is 200/hour and 2,000/day. The boost expires at November 13, 05:00 UTC (midnight New York), restoring voice 20/hour and 100/day, and text 40/hour and 400/day. These counts and the five-minute browser session timer do not cap dollar spend.

## 10–15 minute narrative

**0:00–0:45 — Customer scenario.** “Our fictional rental marketplace helps people choose their next home. Photos leave renters to imagine whether a layout supports their furniture and workday; uncertainty may delay qualified tours and generate suitability questions. Assume a self-hosted Next.js listing app, an existing OpenAI SDK integration, AWS listing/catalog/photo services, MongoDB Atlas, and an identity provider, with review and release work slowing the team. These are scenario assumptions, not claims about a named marketplace. The proposed renter journey is listing → planner → tour inquiry. We want to test that addition without rebuilding the foundation.”

**0:45–1:45 — Architecture.** “Add the new planner on Vercel beside the existing listing experience. Keep the self-hosted listing app, backend APIs, photos, Atlas, and customer identity. Only the planner is new here. The listing-to-tour integration is proposed: this standalone demo uses authored room presets, a catalog fixture, a new demo Atlas cluster with real saves, and signed visitor sessions. The contract is the same for every edit: the model proposes operations, the server validates and saves them, and the browser renders the accepted result.” Show the current/target diagram, then point to **Architecture → System map** if the audience wants the implemented flow.

**1:45–2:45 — Vercel choices.** “I recommend a planner pilot using four demonstrated choices together. Next.js and Functions deliver the planner and enforce its save boundary; AI SDK structures text plans and normalizes voice events; AI Gateway supplies managed model access, routing, and usage visibility; Preview Deployments give reviewers a shareable change before release. Managed Next.js delivery builds on the team's existing framework knowledge, subject to compatibility checks. This addresses both the renter feature and the assumed release bottleneck. We can adopt these separately if discovery changes those assumptions; AI SDK is optional.” Keep the existing-host/OpenAI SDK alternative for discussion below.

**2:45–3:45 — Developer ROI.** “Compare total cost, including senior engineers' time spent maintaining preview environments, cache coordination, release tooling, and model integrations. Time recovered can go into renter experiments; delayed feedback has an opportunity cost. Baseline release and maintenance hours, then value recovered capacity at the customer's loaded hourly cost and subtract incremental platform, model, and migration costs. Recovered hours are capacity; cash savings require an actual spending reduction. We have no measured customer ROI or staffing reduction.” Point to the existing sourced cards: [Fluid Compute](https://vercel.com/docs/functions/usage-and-pricing) pauses CPU billing during I/O waits, while memory during in-flight requests, invocations, and model charges remain; voice media uses Gateway rather than a long-running Function. [Factory's customer story](https://vercel.com/customers/how-factory-scaled-its-cloud-backend-to-one-billion-monthly-requests-on-vercel) illustrates operating without a dedicated infrastructure team, not a staffing guarantee or VoxBuild benchmark.

**3:45–4:15 — Why voice.** “While looking around the room, renters can ask for a change without hunting for every control. That makes voice worth testing, not mandatory. Text and manual controls remain available, and every input meets the same save rules. We'll measure whether voice helps people complete a useful layout, alongside its latency, accessibility, privacy, and cost.”

**4:15–9:15 — Demo.** Close the guide and follow the five-minute path below: Sunlit studio → Midnight style → another lamp → furniture budget → Google-only typed sage-sofa request → inspect returned route and cost → reload → prepared branch Preview URL. This connects renter exploration, grounded AI, managed routing, retained data, and developer review. The routing check is policy-driven, not an outage or voice failover test. Keep voice, invalid edits, and other layouts as optional follow-ups after the core path.

**9:15–10:15 — Success metrics.** “Judge two outcomes together: can the team ship and maintain the feature with less effort, and do eligible renters progress to more qualified tour requests? Baseline review wait, change-to-preview/release time, release and maintenance hours, and on-call work. Compare qualified tour requests per eligible visitor in planner and control cohorts, with suitability-support contacts as a guardrail. Agree sample size, duration, and thresholds before the pilot. Track semantic success, save/reload correctness, and p95 latency. Measure total platform/model cost per accepted interaction, including failed attempts; missing cost stays unknown. Recorded API checks do not establish conversion lift, voice latency, or production reliability.”

**10:15–11:00 — Rollout.** “Integrate the customer's catalog and identity, isolate Preview credentials and data, and validate the full path. Start internally, then with a small eligible cohort. Expand when review/release effort improves, total cost per accepted interaction stays within the agreed budget, and tour-conversion, support, and technical guardrails hold. Keep listing access available. Disable the planner or restore compatible code if needed; code rollback does not undo saved data.” Preview-to-Production promotion, canary exposure, and a timed rollback remain proposed, not demonstrated.

**11:00–12:00 — Risks & limits.** “This is a concept preview, not certified furniture fit or reconstruction from listing photos. Trusted dimensions and collision/circulation validation are future work. Agree privacy, provider-region policy, identity, restricted database connectivity, and spend controls before a pilot. Voice has no automatic in-session failover. If a save response is lost, reload accepted state before retrying; if storage is unavailable, show the error and last acknowledged room.” Retain compatible scene readers during rollback and remove the broad demo Atlas access rule after presenting.

**12:00–12:30 — Tools & ownership.** “I used Codex desktop and role-focused agents for implementation and review, with TypeScript, deterministic tests, build checks, live model checks, and Atlas rereads. I own the decisions and the resulting behavior. The evidence ledger separates instrumented API results from user-confirmed microphone behavior and untested rollout steps. The next decision is a measured pilot of this planner, with the existing marketplace intact.” Show the [public repository](https://github.com/kyuhunlee/voxbuild) and [assessment ledger](assessment.md).

## Five-minute path

Times below restart at zero for the live segment. Use typed prompts for this core path, matching **Case study → Demo**. If limited to ten minutes overall, shorten the architecture and commercial discussion and leave voice, invalid edits, and other layouts for questions.

**0:00 — Establish the customer problem.** “A listing photo tells a tenant what the apartment looks like. It leaves them to imagine whether it can support their furniture and workday. This planner adds that exploration beside the existing listing flow.” Explain that the apartment dimensions are a sample, not measured from a photograph.

**0:25 — Change the mood.** Open Sunlit studio and briefly show its dimensions. Type: “Change the style of the room to midnight.” Point out that the furniture stays intact. Say: “This prompt sends text to a Function. It loads the owned room and catalog, asks a model through AI SDK and Gateway for a bounded plan, then calls the shared validator and Atlas executor in-process. Only the accepted scene returns to the browser.” No partial model output changes the room.

**1:00 — Explore a useful change.** Type: “Add another lamp next to the sofa.” Show the new catalog item while the rest of the design remains intact. Furniture geometry is procedural and maps to known catalog SKUs; this is a concept layout, not a certified fit result.

**1:30 — Answer a grounded question.** Type: “How much does all the furniture cost?” Show the read-only answer from the server-calculated catalog estimate, including the added lamp. Explain that these illustrative prices exclude taxes and delivery; answering does not change the scene revision.

**2:00 — Demonstrate managed routing.** Open **Architecture → Activity → Test Gateway fallback**, switch it on, then **type “Make the sofa sage.”** Say: “This one-request Google-only policy excludes our configured OpenAI primary. Gateway routes to the configured Google fallback; the same validation and Atlas save still apply.” The switch resets after submission. This is genuine policy-driven text routing, not a provider outage simulation or active voice failover.

**2:45 — Inspect the accepted result.** In **Observed activity**, inspect executed model **`google/gemini-2.5-flash`**, provider **Google**, returned usage/cost, duration, operations, and revision. The requested `openai/gpt-4.1-mini` label alone is not execution evidence: use Gateway routing metadata. Treat any missing cost as unknown. The historical routing report recorded `modelAttemptCount: 2`; inspect what this request actually returns.

**3:30 — Prove persistence.** Use **Reload saved room**, then refresh the page. Show the Midnight style, added lamp, sage sofa, and accepted revision after the Atlas read. Explain that the signed visitor cookie scopes ownership; a new private browser session receives its own design.

**4:10 — Show the review workflow.** Switch to the accessible branch Preview URL prepared beforehand. Show the address and explain: “A reviewer can open this branch deployment and review the planner change before release.” Do not imply that merely opening it proves gated promotion, canary rollout, or faster reviews. Keep the demonstrated room in its original tab.

**4:40 — Return to the customer decision.** “The renter can explore a layout and return to a saved design; the team has a reviewable deployment. The new planner runs beside the existing marketplace. Now we can test whether it improves qualified tours and returns engineering time to product work.” Return to **Success metrics**.

## Optional voice and validation walkthroughs

**Voice, if time permits.** This is an important follow-up to the **Why voice** discussion, after the core five-minute path. Return to the original room tab, close the guide, and click the microphone. Say: “Change the room style to Coastal.” Then: “Make the sofa cream.” Wait for the visible change and spoken acknowledgement. Explain: “The microphone button requests a short-lived token from our Function. Audio goes from the browser through Gateway to OpenAI Realtime. A completed tool call comes back through the browser to `/api/commands`, which uses the same validator and Atlas executor. Spoken confirmation follows the save acknowledgement.” Show the Gateway route and requested `openai/gpt-realtime-2.1` model in observed activity. English captions use `gpt-4o-mini-transcribe`; the Realtime model interprets audio independently. Interrupt once, then stop voice and show microphone capture ends. Missing serving-provider or voice-event cost metadata stays unknown. Reload to show the accepted edits remain before returning to the guide.

**Invalid edit, if asked.** Type: “Move the sofa to x=100, y=0, z=0 exactly. If invalid, leave the room unchanged.” A clarification/refusal or rejected command is acceptable; the invariant is that the scene stays unchanged. Use deterministic tests to explain stale revisions and duplicate-command protection. This does not test a provider outage.

## If a live dependency fails

- **Microphone blocked:** continue with the identical text command, acknowledge that voice was not verified in this session, and inspect browser permissions after the presentation.
- **Showing recorded evidence:** open the [assessment ledger](assessment.md) and the matching dated report. Keep instrumented storage/text results, synthetic Gateway voice integration, and user-confirmed microphone behavior distinct. Historical direct-provider voice checks do not establish the current Gateway browser path.
- **Gateway unavailable:** demonstrate manual validated controls and the last real report. Do not present canned local previews as live model responses.
- **Atlas unavailable:** show the recoverable error and the last accepted state. Sample mode is a separately labeled local walkthrough, not a persistence fallback.
- **Text response lost:** reload the saved room to determine whether the edit committed. Retrying a text request with the old revision returns `409 REVISION_CONFLICT` after a successful commit; receipt-based replay applies to identical manual/voice operation requests, not the whole text-generation endpoint.

## Technical discussion prompts

- **“Can we keep our host and OpenAI SDK?”** Yes. Gateway can work with the existing OpenAI SDK on the existing host; AI SDK and Vercel hosting are separate adoption decisions. If the current delivery platform meets the need, Gateway alone may be the smaller useful change. This scenario also assumes a review/release bottleneck, which is why the lead recommendation pilots managed delivery and the AI integration together for the new planner.
- **“No data leaves our region.”** Functions and Atlas placement do not constrain Gateway media routing or model-provider processing. Start by defining data classes and allowed providers/regions; disable voice until the permitted media path is established.
- **“The budget is halved.”** Preserve manual controls and the saved-scene contract; measure text models on the same semantic suite, shorten voice sessions, and use account/project spend limits. Do not remove validation or silently weaken ownership.
- **“Can this prove that my furniture fits?”** It can show catalog dimensions in a known sample room. Real fit needs trusted room measurements, exact assets, collision and circulation validation, and clear product language.
- **“Why no Workflow?”** The core edit is short and atomically committed. Long-running photo reconstruction or human approval would change the durability requirements and justify a workflow.

End by showing evidence and limitations, not an unverified claim about adoption or production readiness. After the demo, explicitly remove the approved Atlas `0.0.0.0/0` access-list rule; it has no automatic expiry.
